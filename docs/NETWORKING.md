# Сеть: DNS, локальный backend и границы проксирования

## DNS: наблюдение и точечная блокировка

В `[dns]` доступны `log_queries = true` и `block_hosts = ["report.appmetrica.yandex.net"]`. Список по умолчанию пуст: пример — кандидат для проверки, не готовый безопасный список телеметрии. Имена точные, без wildcard; блокировка одного имени не блокирует поддомены. Пересечение с `rewrite_hosts` и дубликаты запрещены.

- `BLOCK` возвращает NXDOMAIN для всех IN-типов без upstream-запроса; не подменяет ответ HTTP-заглушкой.
- `REWRITE`, `FORWARD`, `BLOCK` пишут только имя, тип, транспорт, rcode и длительность. Не пишут пакеты/ответы/идентификаторы клиентов. До 100 записей/сек на процесс; лишние записи пропускаются. DNS-имена тоже могут быть чувствительными — включайте журнал временно, не публикуйте без проверки.
- `docker compose kill -s HUP quasard` перечитывает DNS; ошибочная конфигурация сохраняет последнюю рабочую политику. LLM/MCP/TTS этим сигналом не обновляются.
- Сначала наблюдайте, затем блокируйте по одному домену и проверяйте запуск, голос и музыку. Не блокируйте целиком `yandex.net`, авторизацию, Quasar/UniProxy или обновления без отдельной проверки.
- DNS не показывает все соединения: кеш, IP напрямую, DoH/DoT/другой DNS обходят наблюдение. Docker Desktop NAT может скрывать исходный IP; журнал не доказывает, что запрос пришёл именно от Станции. Для полной картины нужен отдельный ограниченный захват на своей станции/роутере.

## 1. Что умеет текущий сервер

`quasard` — локальный backend с HTTP-моками и голосовым WebSocket `/uni.ws`, с опциональным DNS-forwarder в том же процессе. DNS по умолчанию выключен; включение и точечные rewrites — секция `[dns]`, обновление через SIGHUP. Он **не reverse proxy и не маршрутизатор**.

- `internal/httpapi/httpapi.go` обрабатывает известные пути активации, конфигурации, OAuth, метрик и OTA. Многие ответы — заглушки, не облачные сервисы.
- Поддерживается `Host` и префикс пути вида `/quasar.yandex.net/register`: префикс превращается в имя хоста, остаток — в локальный путь. Это совместимость с внешним прокси, **не пересылка запроса**. Префикс не является allowlist доменов.
- Неизвестный HTTP-путь получает catch-all `200 {"status":"ok"}`, а не ответ настоящего upstream. Поэтому «открывается любой URL» не означает рабочий passthrough.
- Код содержит заготовки push; наличие имени `push.yandex.ru` в списке сертификата не гарантирует готовый push-сервис. В текущем Go-запуске отдельный `PushWebSocket` hook не подключён.
- Обращения backend к LLM, Яндекс Музыке и другим настроенным API — отдельные исходящие соединения сервера, **не проксирование произвольных запросов Станции**. Локальность зависит и от выбранных моделей/API.

После DNS-подмены клиент соединяется с IP `quasard`, сохраняя исходное имя HTTP Host и TLS SNI. Другие домены продолжают разрешаться через обычный upstream, а прикладные соединения к ним идут **DIRECT** через обычный шлюз, не через `quasard`. DNS-запрос при этом может проходить через Keenetic и отдельный резолвер. **DNS ≠ прокси**: такая схема не изолирует Станцию от интернета, не отключает все обновления и не подтверждает утверждение «наружу больше не ходит».

Для настройки только одной Станции используйте [руководство Keenetic](KEENETIC.md): зарегистрированный `MAC` → закреплённый `STATION_IP` → персональный DNS-профиль → встроенный DNS quasard с точными rewrites. Другим клиентам профиль не назначается. Отдельный AdGuard Home остаётся альтернативой, если DNS уже развёрнут.

## 2. Какие имена перенаправлять

Источники: `config.example.toml`, `internal/httpapi/httpapi.go`, `internal/store/store.go`, генераторы сертификатов и `KNOWN_HOSTS` исторического `alice_server/http_api.py` из reference commit `a142b19c997f3a8a4bed8f6b0aef4acd70e2436e` (Python удалён из активного дерева). Список известных имён/SAN — **не доказательство**, что все эти сервисы реализованы и должны перенаправляться.

| Точное имя | Роль и когда нужно |
| --- | --- |
| `quasar.yandex.net` | Основной кандидат: регистрация, `get_sync_info`, состояние устройства. Начните с него для локальной конфигурации. |
| `quasar.yandex.ru` | Вариант quasar; добавляйте, если его использует ваша прошивка. |
| `uniproxy.alice.yandex.net` | Голосовой `/uni.ws`. Нужен при стандартном `wss://uniproxy.alice.yandex.net/uni.ws` в `uniProxyUrl`; при своём URL направьте именно его имя на сервер. |
| `oauth.yandex.ru`, `login.yandex.ru` | Условно нужны для активации/авторизации. Здесь моки `/token`, `/x_token` и ряда passport-путей, не настоящий login. Не отправляйте реальные пароли в локальные заглушки. |
| `mobileproxy.passport.yandex.net` | Условный passport/bootstrap для соответствующих прошивок; добавляйте по запросам устройства. |
| `startup.mobile.yandex.net` | Условный bootstrap `/analytics/startup`, может понадобиться при старте. |
| `report.appmetrica.yandex.net`, `analytics.mobile.yandex.net`, `clck.yandex.net` | Необязательные для базового голосового пути метрики/проверки. Перенаправление обслуживает только известные заглушки, не весь сервис. |
| `push.yandex.ru`, `scbh.yandex.net`, `rpc.alice.yandex.net` | Дополнительные имена из списка совместимости. Только по подтверждённой потребности; не обещают полный push/RPC. |
| `uniproxy-quic.alice.yandex.net` | Дополнительный транспорт некоторых прошивок. HTTPS/WebSocket поверх TCP не заменяет QUIC/UDP; одна DNS-запись поддержку QUIC не добавляет. |
| `updater.mobile.yandex.net` | OTA: известные update-пути возвращают пустой/отключённый результат. Не добавляйте ради обычного голосового теста; DNS-rewrite не гарантирует блокировку всех каналов обновления. |

Практический порядок:

1. Начните с `quasar.yandex.net` и `uniproxy.alice.yandex.net` для стандартной конфигурации; добавьте вариант `.ru`, если он действительно используется.
2. Если Станция ещё не активирована или не получает конфигурацию, сопоставьте её запросы с OAuth/bootstrap-строками таблицы. Минимум зависит от модели, состояния и прошивки; универсальный обязательный список не установлен.
3. Остальные имена добавляйте по одному с проверкой результата. Отсутствующий endpoint не исправляется расширением DNS-списка. Не перенаправляйте `yandex.ru`, `yandex.net`, их поддомены целиком, CDN или все неизвестные имена. Домены LLM/музыки, используемые самим сервером, тоже не надо направлять обратно в него.
4. Для каждого выбранного имени проверьте A **и AAAA**, поддомены и сохранённые ответы. Отдельно учтите IPv6 DNS, DoH/DoT, жёстко заданные IP/DNS и fallback. Подробнее — [проверка Keenetic](KEENETIC.md#4-проверить-по-слоям).

## 3. Порты и TLS до переключения DNS

Обозначения `MAC`, `STATION_IP`, `SERVER_IP`, `DNS_IP` определены в [подготовке](KEENETIC.md#1-проверить-условия-и-сохранить-исходное-состояние). Ниже — план ручной настройки после отдельного разрешения, **не выполненные изменения**.

### DNS не передаёт порт

A/AAAA содержат IP, не `IP:порт`. Подмена имени не превращает `https://host/` в `https://host:8443/`: обычные HTTP/HTTPS-клиенты используют **80/443**. В текущем `compose.yaml` опубликованы только:

```text
127.0.0.1:8080 → контейнер:8080
127.0.0.1:8443 → контейнер:8443
```

Это безопасный локальный режим, недоступный Станции по LAN. Внутренний `server.host = "0.0.0.0"` в контейнере не означает публикацию на всех интерфейсах хоста. Python-пример в `config.example.toml` с 80/443 не отменяет Go/Compose-настройки в `config.go.example.toml`.

Для Станции на обычных URL нужен отдельно согласованный LAN-вход `SERVER_IP:80/443`: например, точечная Docker-публикация на 8080/8443 контейнера. Внешний TLS-прокси — другой возможный компонент, но проект его не поставляет; его настройка и безопасность отдельны.

### Опциональный Compose override: только пример

**Не меняйте базовый `compose.yaml` и не открывайте WAN.** Сначала проверьте свободные порты 80/443, наличие у хоста `SERVER_IP` и правила доступа. Публикация открывает также административные HTTP-пути проекта: ограничьте LAN-вход Станцией и разрешённым администратором; сам bind на LAN-IP не ограничивает источники. У Docker правила публикации могут обходить часть host firewall — проверьте фактический доступ, а не только наличие правила.

После разрешения оператор может вручную создать отдельный `compose.lan.yaml` со следующим содержимым, заменив `SERVER_IP` **в тексте** на IPv4 хоста. Этот файл руководством не создаётся:

```yaml
services:
  quasard:
    ports: !override
      - "127.0.0.1:8080:8080"
      - "127.0.0.1:8443:8443"
      - "SERVER_IP:80:8080"
      - "SERVER_IP:443:8443"
```

`!override` требует Docker Compose **2.24.4+** и заменяет список целиком; loopback-публикации сохранены явно. Без него обычное объединение файлов может **добавить**, а не заменить порты. На старом Compose остановитесь и выберите отдельно проверенный способ; не удаляйте тег вслепую.

1. Проверьте версию и итоговый план **без запуска**:

   ```sh
   docker compose version
   docker compose -f compose.yaml -f compose.lan.yaml config
   ```

   Запускайте из корня проекта. Вывод `config` может содержать подставленные секреты, не публикуйте его. Убедитесь, что нет `0.0.0.0`, `[::]`, host networking или посторонних публикаций. Не добавляйте port forwarding/UPnP на WAN.
2. Только после проверки и разрешения примените план:

   ```sh
   docker compose -f compose.yaml -f compose.lan.yaml up -d
   ```

   Этот шаг может собрать/скачать образ и пересоздать сервис. Данные, модели, сертификаты и работоспособный образ должны быть подготовлены отдельно; override не устанавливает их и не создаёт DNS.
3. При откате **сначала верните DNS-профиль Станции**, как в [порядке отката](KEENETIC.md#5-откат-сначала-вернуть-обычный-dns). Затем запуск только базового файла вернёт исходные loopback-порты:

   ```sh
   docker compose -f compose.yaml up -d
   ```

   Проверьте результат; удалите только свой override и собственные правила доступа. Не используйте очистку всех firewall/NAT или `down -v` ради удаления двух публикаций.

Справка: [Docker Compose: merge, `!override`](https://docs.docker.com/reference/compose-file/merge/#replace-value).

### `uniProxyUrl` — отдельный адрес, не DNS-настройка

`server.public_uniproxy_url` (или `ALICE_SERVER_PUBLIC_UNIPROXY_URL` в окружении процесса) переопределяет `get_sync_info → config.system_config.uniProxyUrl`. Пустое значение оставляет стандартный URL в конфигурации; для новой записи это `wss://uniproxy.alice.yandex.net/uni.ws`. Если в сохранённой конфигурации устройства уже другой URL, проверяйте фактический ответ: пустое значение не обязано сбрасывать его.

- При LAN-входе на 443 можно оставить стандартный URL и rewrite его имени на `SERVER_IP`.
- Явный `wss://uniproxy.alice.yandex.net:8443/uni.ws` требует доступного Станции LAN-порта 8443. Базовый loopback-порт для этого **недостаточен**. Показанный override открывает LAN 443, не LAN 8443.
- Свой hostname требует собственного DNS-ответа и сертификата с этим SAN. URL с IP требует IP SAN и доверия клиента. Не используйте адрес `127.0.0.1`: для Станции это сама Станция.
- Изменение только `uniProxyUrl` не переносит начальные quasar/OAuth-запросы с 443 на 8443 и может не поддерживаться конкретной прошивкой. Проверьте, что Станция получила и использовала ответ, а не старый кэш.
- Экспорт переменной в shell не гарантирует передачу в контейнер: текущий Compose явно перечисляет только LLM-переменные. Изменение окружения сервиса/конфига — отдельная согласованная настройка.

### TLS — обязательная предпосылка, не автоматический эффект DNS

1. Для каждого HTTPS/WSS-имени нужен сертификат с подходящим SAN, корректная цепочка, срок действия и часы устройства. Сохранение Host/SNI при DNS-подмене не отменяет проверку сертификата.
2. Генераторы сертификатов проекта создают локальные CA/серверные файлы. Они **не устанавливают доверие на Станцию или Keenetic**. Установка CA только на ПК не делает сертификат доверенным Станции. Не ставьте тестовый CA на все устройства сети и не распространяйте его приватный ключ.
3. Сначала установите, допускает ли ваша Станция/прошивка такой доверенный TLS-путь. Certificate pinning или закрытое хранилище доверия могут исключать этот способ; универсальной инструкции обхода здесь нет. Не отключайте проверку TLS как решение.
4. В Go HTTPS может не запуститься при отсутствующем `certfile`: публикация 443 сама по себе не создаёт TLS-listener. Проверьте журнал запуска, доступность сертификата и ключа контейнеру, затем сертификат с исходным SNI. HTTP-healthcheck не доказывает готовность HTTPS.
5. Только затем переключайте DNS одной Станции. Прошедшая проверка с ПК подтверждает доверие **ПК**, а не Станции.

## 4. Проверка и диагностика

Проверки ниже оператор выполняет вручную после разрешения сетевых обращений; при подготовке этих документов они против LAN не запускались.

1. Сначала проверьте отдельный резолвер: точный A → `SERVER_IP`, согласованный AAAA, обычный ответ для неперечисленного имени; затем назначение профиля и запросы именно Станции. Подробный порядок и команды — в [KEENETIC.md](KEENETIC.md#4-проверить-по-слоям).
2. После разрешённого LAN-входа можно проверить TLS с тестового компьютера **без смены его DNS**. Подставьте LAN IP вместо `SERVER_IP`, путь к доверенному для теста CA вместо `CA_FILE`:

   ```sh
   curl --resolve quasar.yandex.net:443:SERVER_IP --cacert CA_FILE https://quasar.yandex.net/_status
   ```

   `--resolve` сохраняет имя/SNI, а `--cacert` ограничивает тестовое доверие этим вызовом. Не подменяйте проверку `-k`. Это проверяет обработчик `/_status` через TLS, не готовность моделей и не доверие Станции. Дополнительно проверьте `/readyz` (реализован в Go backend), реальную конфигурацию устройства и WebSocket.
3. После DNS-переключения сопоставьте журнал DNS и подключения backend. Трафик не появился — проверьте кэш, другой DNS/IPv6, DHCP, профиль, firewall и TLS; не расширяйте сразу домены до wildcard. Сервер DNS может видеть только IP роутера.
4. Другой клиент должен сохранить прежний профиль, обычное разрешение этих доменов и обычную работу приложений. Если тоже получает `SERVER_IP`, проверьте общий DNS/DHCP, общий rewrite, профиль сегмента и ранее сохранённые записи.
5. При сбое выделенного DNS заранее определите поведение: отказ разрешения или обход через резервный DNS. Публичный fallback может вернуть реальный облачный адрес. Отдельно проверьте DoH/DoT, AAAA и жёстко заданные IP; эти пути не исправляются одним A-rewrite.

## 5. Можно ли неизвестные запросы отправлять в настоящий сервис?

**Сейчас — нет.** Catch-all поглощает неизвестный HTTP-запрос локальным `200`, а DNS не может выбрать backend по HTTP-пути. Чтобы остальные сервисы продолжали работать без участия `quasard`, не перенаправляйте их имена: пусть DNS разрешает их нормально, а Станция ходит DIRECT.

Будущий passthrough — **отдельная функция/компонент**, не настройка существующего мока. Перед разработкой нужны как минимум:

1. **Явный allowlist** точных upstream-имён, портов и при необходимости путей/методов. Не превращать клиентские `Host`, префикс пути, URL или `CONNECT` в произвольный upstream; неизвестное отклонять, а не проксировать автоматически. Предусмотреть журнал и понятный отказ вместо маскирующего `200`.
2. **Выбор TLS-границы.** L4 passthrough сохраняет сквозной TLS, но не позволяет одновременно мокать отдельные HTTP-пути того же зашифрованного соединения. Для разделения по путям нужен TLS termination с доверием Станции и учётом pinning; наружу — новый TLS-сеанс с проверкой цепочки и правильным SNI. Не отключать upstream TLS-проверку.
3. **Независимый upstream DNS.** Разрешение настоящего сервиса не должно использовать тот же rewrite и возвращать `SERVER_IP`, loopback или сам прокси. Учесть AAAA, bootstrap, кэш, смену IP, split DNS и DNS rebinding; проверять каждый выбранный адрес и адрес после redirect. Слепая фиксация одного CDN-IP — тоже не надёжное решение.
4. **Защита от SSRF/open proxy.** Запретить обращения к localhost, LAN, link-local, metadata и другим специальным диапазонам, включая IPv6/IPv4-mapped; частные upstream допустимы лишь как отдельно заданные доверенные назначения. Контролировать redirects, DNS-ответы и реальные адреса соединения. Ограничить исходящий доступ сетевыми правилами.
5. **Границы HTTP/WebSocket.** Корректно обрабатывать Host/SNI, hop-by-hop заголовки и Upgrade, размеры тела, таймауты, соединения, ошибки и повторные запросы. Не утекать OAuth/токенами в логи или на другой upstream; ограничить доступ к самому прокси. TCP HTTP-прокси не добавляет QUIC/UDP.

Ни passthrough, ни его DNS/TLS-компоненты этим документом не реализуются. Сначала нужна отдельная спецификация и разрешение на изменения; текущий безопасный путь — узкий DNS-список и DIRECT для остального.
