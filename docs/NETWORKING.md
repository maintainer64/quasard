# Сеть: DNS и локальный сервер

[Основная настройка и единый рецепт Compose](../README.md) · [CA Станции](STATION_CA.md) · [Keenetic](KEENETIC.md) · [Диагностика и HAR](TRAFFIC_CAPTURE.md)

`quasard` — локальный HTTP-backend с моками и голосовым WebSocket `/uni.ws`. В том же процессе есть необязательный DNS-forwarder. Это **не полный HTTP-прокси, не маршрутизатор и не прозрачная замена облака**.

Своя Станция Лайт уже работала с проектом. Полная совместимость функций, других устройств и прошивок не подтверждена; результаты симуляторов тоже не заменяют проверку реального устройства. См. [parity](parity.md).

## Что делает DNS

DNS по умолчанию выключен. Для базового сценария используются только два точных имени:

| Имя | A | AAAA при пустом `answer_ipv6` |
| --- | --- | --- |
| `quasar.yandex.net` | LAN IPv4 хоста quasard | NODATA |
| `uniproxy.alice.yandex.net` | LAN IPv4 хоста quasard | NODATA |

NODATA — успешный DNS-ответ (`NOERROR`) без записи запрошенного типа, не `NXDOMAIN`. Для переписанного имени AAAA не уходит к upstream, поэтому облачный IPv6 не подмешивается. Если оператор явно задаст `answer_ipv6`, сервер вернёт этот адрес; он должен быть доступен Станции и защищён отдельно.

Правила работают с точными именами, без wildcard и автоматического охвата поддоменов. Для переписанных имён обычные остальные IN-типы, в том числе HTTPS/SVCB, получают NODATA; transfer-запросы AXFR/IXFR отклоняются. Обычные запросы других имён пересылаются настроенным upstream; невалидные и неподдерживаемые запросы могут быть отклонены. Успешный forward не означает, что последующее соединение пройдёт через quasard: устройство обращается к полученному адресу напрямую.

Минимальная политика в секции `[dns]` уже используемого конфигурационного файла:

```toml
[dns]
enabled = true
listen = "0.0.0.0:5353"
upstreams = ["1.1.1.1:53", "9.9.9.9:53"]
answer_ipv4 = "HOST_IP"
answer_ipv6 = ""
rewrite_hosts = ["quasar.yandex.net", "uniproxy.alice.yandex.net"]
block_hosts = []
log_queries = false
allow_cidrs = ["STATION_IP/32"]
```

`HOST_IP` и `STATION_IP` — обозначения, не допустимые буквальные значения: замените их на LAN IPv4 хоста и Станции. Не создавайте вторую секцию `[dns]`. Остальные параметры и пределы указаны в [config.example.toml](../config.example.toml).

Порт `5353` в примере — внутренний порт процесса; Станция должна получать DNS на `HOST_IP:53` по UDP и TCP. Публикацию портов, конфигурационный файл, сертификаты и запуск контейнера настраивайте **по единому рецепту в [README](../README.md)**. Здесь нет отдельного Compose override или альтернативного способа запуска. DNS не меняет HTTP/TLS-порты: для реальной Станции обычно нужны доступные порты 80/443; localhost-публикация 8080/8443 сама по себе этого не обеспечивает.

Upstream должен разрешать имена независимо от локальной подмены. Если Keenetic использует quasard как DNS, нельзя отправлять upstream-запросы quasard обратно этому Keenetic: возникнет цикл. Публичный upstream допустим; публичный «запасной DNS» непосредственно у Станции может обойти rewrite.

## Доступ и Docker NAT

- Ограничьте DNS доверенными клиентами через `allow_cidrs` и firewall. Для одной Станции начните с её закреплённого IPv4 `/32`.
- Не публикуйте DNS в WAN и не открывайте рекурсию всем адресам. DNS не проверяет владельца устройства; `/32` — фильтр источника, не аутентификация.
- Docker NAT, особенно Docker Desktop, может заменить видимый исходный IP адресом gateway. Тогда ACL по IP Станции не пропустит запрос. Это не повод без проверки разрешать подсеть Docker, весь LAN или `0.0.0.0/0`.
- Сначала выясните, какой источник видит контейнер. Если исходный адрес теряется, выберите поддерживаемую схему с сохранением адреса либо отдельно ограничьте клиентов **до NAT**, затем проверьте запрет для постороннего клиента. Разрешение одного NAT gateway само по себе не ограничивает доступ одной Станцией.
- DNS-журнал не содержит адрес клиента и не помогает удостоверить источник. Диагностика источника требует отдельных локальных средств; не публикуйте захват без очистки.

## Проверка DNS

С разрешённого в ACL компьютера, где есть `dig`, выполните:

```sh
dig @HOST_IP quasar.yandex.net A
dig @HOST_IP uniproxy.alice.yandex.net A
dig @HOST_IP quasar.yandex.net AAAA
dig @HOST_IP uniproxy.alice.yandex.net AAAA
dig +tcp @HOST_IP quasar.yandex.net A
dig @HOST_IP example.org A
```

Замените `HOST_IP` адресом сервера. Первые два ответа должны содержать его LAN IPv4. При пустом `answer_ipv6` оба AAAA-запроса должны вернуть `status: NOERROR` и `ANSWER: 0`. TCP тоже должен работать; последнее имя проверяет forward.

Компьютер для проверки нужно разрешить отдельно и временно; не расширяйте ACL на всю сеть ради теста. Удалите временное разрешение после проверки. Затем переподключите Станцию и проверьте её фактическую работу: тест с компьютера не подтверждает настройки клиента, TLS или голосовой цикл.

## DNS-журнал и блокировка

`log_queries = true` включает журнал метаданных:

- `REWRITE`, `FORWARD`, `BLOCK`;
- имя запроса, тип, UDP/TCP, код ответа и длительность;
- без содержимого пакетов, ответов и идентификаторов клиента.

Предел — 100 записей в секунду на процесс, лишние записи пропускаются. Это предел журнала, не история всех запросов и не HTTP traffic capture. Сами DNS-имена могут раскрывать личные данные; включайте журнал временно и проверяйте перед передачей кому-либо.

`block_hosts` по умолчанию пуст. Каждое указанное точное имя получает `NXDOMAIN` для всех IN-типов без обращения к upstream. Поддомены не блокируются автоматически; дубликаты и пересечение с `rewrite_hosts` запрещены. Блокировка DNS не подменяет HTTP-ответ и не закрывает соединения по уже известным IP.

Сначала наблюдайте, затем при необходимости добавляйте по одному имени и проверяйте запуск, голос и музыку. Не переносите чужой список блокировки вслепую: он может сломать авторизацию, обновления или нужные функции. При ошибке удалите добавленное правило и повторите проверку.

DNS не видит обращения из кеша, соединения по IP, DoH/DoT и другой DNS. Поэтому журнал не доказывает отсутствие исходящего трафика или обращений к облаку.

## Перечитать настройки DNS

После изменения смонтированного конфигурационного файла отправьте SIGHUP сервису основного Compose-проекта. Используйте тот же набор Compose-файлов, что при запуске; команда для стандартного вызова:

```sh
docker compose kill -s HUP quasard
```

SIGHUP перечитывает **только DNS**, включая настройки доступа, rewrite, блокировки и журнал. Ошибка чтения, проверки или применения оставляет последнюю рабочую DNS-политику; проверьте результат в логе, не считайте отправку сигнала подтверждением успеха. Переменные окружения имеют приоритет над файлом и не меняются от сигнала.

LLM, MCP, TTS и HTTP/TLS этим способом не перенастраиваются. Публикация портов Docker тоже не меняется: для неё требуется пересоздание контейнера по основной инструкции. Чтобы замена файла была видна процессу, используйте способ монтирования из основного рецепта; атомарная замена одиночного bind-mounted файла может оставить контейнер со старым содержимым.

Отдельные защитные пределы DNS — таймаут upstream, число одновременных запросов и TCP-соединений, общий `rate_limit` для UDP+TCP. При превышении лимита запросов UDP-пакеты отбрасываются, TCP-соединение закрывается. Это не блокировка домена и не обязательно ошибка rewrite.

## HTTP/TLS — отдельный слой

DNS возвращает адрес, но не устанавливает доверие сертификату и не решает certificate pinning. Собственный CA и настройка доверия Станции описаны в [STATION_CA.md](STATION_CA.md); CA роутеру для выдачи DNS не нужен. Не отключайте проверку TLS глобально и не используйте чужие приватные ключи.

HTTP-обработчики отвечают на известные запросы активации, конфигурации, OAuth, метрик и OTA; многие ответы — моки. Неизвестный путь может получить `200 {"status":"ok"}`, а не реальный облачный ответ. Сервер не пересылает произвольный HTTP/HTTPS к Яндексу и не записывает полный HAR.

Поле `server.public_uniproxy_url` задаёт `uniProxyUrl`, выдаваемый устройству в sync info; его значение должно соответствовать доступному TLS endpoint. Перед переходом на обычную сеть **сначала восстановите DNS и переподключите клиентов, затем останавливайте quasard**. Порядок для Keenetic — в [отдельной инструкции](KEENETIC.md).
