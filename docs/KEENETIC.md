# Keenetic: DNS-подмена только для своей Станции

Цель: выбранные **точные имена** ведут на `quasard` только у одной Станции. Остальные DNS-запросы разрешаются обычным способом; остальной прикладной трафик идёт **DIRECT**, не через `quasard`. DNS — не прокси, не запрет интернета и не гарантия отсутствия обращений к Яндексу.

Это инструкция для ручного, отдельно согласованного изменения своей сети. Добавление документа **не меняет** роутер, DNS, сертификаты или контейнеры. Команды ниже — примеры для оператора, не результат выполненной настройки.

## 1. Проверить условия и сохранить исходное состояние

1. Нужен KeeneticOS **3.8+** с пользовательскими DNS-профилями для зарегистрированных клиентов. Проверьте возможности своей версии; названия страниц и доступность функций различаются. Ссылки на KN-1811 ниже — документация, не требование этой модели и не универсальная карта меню.
2. Сохраните резервную копию конфигурации роутера и текущие настройки DNS/интернет-фильтров, DHCP, IPv6, профиля Станции. Запишите настройки портов контейнера, firewall и список уже существующих DNS-rewrite в резолвере. Копии могут содержать секреты: храните закрыто.
3. Подготовьте локальный доступ к управлению роутером с **другого** устройства. Не меняйте профиль всей домашней сети ради теста одной Станции.
4. Заполните обозначения; это не готовые адреса:

   | Обозначение | Значение |
   | --- | --- |
   | `MAC` | MAC активного интерфейса своей Станции, проверенный по списку клиентов |
   | `STATION_IP` | закреплённый DHCP IPv4 Станции |
   | `SERVER_IP` | постоянный LAN IPv4 хоста `quasard`, не `127.0.0.1` и не IP контейнера |
   | `DNS_IP` | LAN IPv4 DNS quasard, обычно совпадает с `SERVER_IP`; отдельный резолвер тоже допустим |
   | `ROUTER_IP` | LAN IPv4 Keenetic |

5. Зарегистрируйте Станцию в Keenetic по `MAC`, закрепите `STATION_IP`; исключите конфликт адресов. При смене Wi-Fi/Ethernet проверьте MAC заново. Это идентификация клиента роутером, **не** DNS-правило по MAC.
6. Сначала выполните условия [портов и TLS](NETWORKING.md#3-порты-и-tls-до-переключения-dns). По умолчанию Compose публикует только `127.0.0.1:8080` и `127.0.0.1:8443`: Станции они недоступны. Без доверенного Станцией сертификата DNS-подмена HTTPS недостаточна. Генератор сертификатов не устанавливает CA на устройство; pinning может сделать схему невозможной.

**Стоп-условие:** нет нужного DNS-профиля, доверия TLS или контролируемого LAN-доступа — не переключайте DNS. Не заменяйте это глобальной подменой всех доменов.

## 2. Включить DNS quasard

Рекомендуемая схема: зарегистрированный клиент → его DNS-профиль Keenetic → **DNS в quasard** → точные rewrites либо обычные upstream DNS. Отдельный AdGuard Home не нужен; существующий внешний resolver остаётся альтернативой.

1. Настройте DNS на сервере по [инструкции запуска](../README.md#встроенный-dns). Нужен постоянный `DNS_IP`; UDP **и** TCP53 доступны только нужным LAN-источникам. Не публикуйте53 в WAN; сначала проверьте конфликт с существующим DNS.
2. В `[dns]` укажите `answer_ipv4 = "SERVER_IP"`, `rewrite_hosts = ["quasar.yandex.net", "uniproxy.alice.yandex.net"]` и явный `allow_cidrs`. Подставьте реальные адреса; `SERVER_IP` здесь placeholder. Upstreams — numeric IP:port без цепочки `Keenetic → quasard → Keenetic`.
3. Начальная пара доменов не гарантирует активацию любой прошивки. Добавляйте остальные точные имена по [их роли](NETWORKING.md#2-какие-имена-перенаправлять), не весь список SAN и не wildcard. Поддомены не захватываются.
4. Без `answer_ipv6` выбранные имена получают пустой AAAA (NOERROR/NODATA); HTTPS/SVCB и прочие типы для этих имён тоже не пересылаются в облако. Если нужен IPv6, задайте рабочий LAN IPv6 сервера и проверьте его доступность. Неперечисленные имена идут upstream.
5. После изменения файла отправьте SIGHUP: обновляется только DNS, без перезапуска моделей. При ошибке остаются предыдущие правила. TTL и кэш клиента могут задержать видимый результат.

ACL проверяет IP источника, **не MAC**. Keenetic или Docker Desktop могут заменить IP Станции на IP роутера/шлюза. Проверяйте фактический источник; не расширяйте ACL до всех адресов. Изоляцию между домашними клиентами обеспечивает назначение профиля только Станции на Keenetic, а не распознавание MAC сервером. ACL не аутентифицирует spoofed UDP; доступ53 ограничьте и на сетевом уровне.

## 3. Назначить пользовательский DNS-профиль только Станции

1. В доступных на вашей версии настройках DNS/интернет-фильтров создайте отдельный пользовательский профиль, например `quasard-station`.
2. Явно задайте для него `DNS_IP` как пользовательский DNS-сервер. **Пустой профиль «без фильтрации» не равен профилю с вашим резолвером**: он может использовать DNS провайдера/общие серверы. Не добавляйте публичный DNS вторым сервером как якобы безопасный резерв: он может обслуживать запросы в обход rewrite.
3. В списке профилей **зарегистрированных клиентов** назначьте профиль только записи `MAC` / `STATION_IP`. Профиль по умолчанию сегмента, других клиентов и глобальные DNS оставьте прежними. Сохраните через интерфейс своей версии.
4. Не подменяйте этот шаг полем DNS в DHCP **всего сегмента**. Такое поле выдаёт DNS всем его DHCP-клиентам и направляет запросы прямо к указанному серверу, а не к DNS-прокси Keenetic. Это другая область действия.
5. Учитывайте вручную заданный DNS, жёстко заданные внешние DNS, DoH/DoT и IPv6 DNS на Станции. Они могут обойти профиль. Назначение профиля само по себе не доказывает перехват всех способов разрешения. Если нужен запрет обхода, проектируйте отдельную политику только для Станции; глобальные правила перехвата/блокировки здесь не предлагаются.

Официальная основа: [профиль с пользовательскими DNS, KeeneticOS 3.8+](https://support.keenetic.ru/ultra/kn-1811/ru/37168-creating-a-dns-profile-without-filtering.html), [интернет-фильтры и профили клиентов](https://support.keenetic.ru/ultra/kn-1811/ru/24580-internet-safety--content-filtering-.html), [отличие DHCP DNS сегмента от DNS-прокси роутера](https://support.keenetic.ru/ultra/kn-1811/ru/19399-ways-to-add-custom-dns-servers.html).

## 4. Проверить по слоям

Выполняйте после отдельного согласия на сетевой тест. В командах замените обозначения своими адресами. `dig` — необязательная утилита; те же A/AAAA можно проверить другим DNS-клиентом.

1. **Резолвер до назначения профиля.** С разрешённого тестового хоста запросите выделенный DNS напрямую:

   ```sh
   dig @DNS_IP quasar.yandex.net A
   dig @DNS_IP quasar.yandex.net AAAA
   dig @DNS_IP uniproxy.alice.yandex.net A
   dig @DNS_IP example.org A
   dig @DNS_IP example.org AAAA
   dig @DNS_IP probe.quasar.yandex.net A
   ```

   Точные имена дают ожидаемые ответы; неперечисленные имя и поддомен не получают `SERVER_IP` из широкой подмены. Публичный AAAA для перехваченного имени — повод остановиться. Прямой запрос к `DNS_IP` **не проверяет** назначение профиля Станции.
2. **Фактический путь Станции.** После назначения профиля обновите её DHCP/соединение и DNS-кэш доступным способом; при необходимости перезапустите только Станцию. Очистите относящиеся к тесту кэши роутера/резолвера штатным способом либо дождитесь TTL. Проверьте DNS-ответ с самой Станции и подключения `quasard`, чтобы подтвердить нужный путь. Встроенный DNS не пишет журнал каждого запроса; у внешнего resolver можно использовать его журнал. Отсутствие MAC в DNS-журнале нормально; запись с IP роутера сама по себе не доказывает источник.
3. **HTTP/TLS.** Отдельно проверьте TCP 80/443, имя/SNI, доверие цепочке, затем `get_sync_info` и фактический `uniProxyUrl`/WebSocket `/uni.ws`. Ответ `200 {"status":"ok"}` на случайный URL — catch-all мок, не доказательство проксирования или полной работоспособности. Ошибка сертификата не исправляется дополнительными DNS-записями.
4. **Остальная сеть.** На другом клиенте оставьте обычный DNS и профиль. Убедитесь, что выбранные домены там имеют обычные ответы, а не `SERVER_IP`, и обычные приложения работают. Не используйте прямой запрос к `DNS_IP` как тест изоляции: он намеренно обращается к тому же резолверу.
5. **Обходы и сбои.** Проверьте A/AAAA, DNS по IPv6, DoH/DoT, альтернативный DNS, старые кэши и поведение при недоступном резолвере. Не выдавайте успешный тест DNS за доказательство блокировки OTA или отсутствия внешнего трафика. Не провоцируйте обновление прошивки ради проверки.

## 5. Откат: сначала вернуть обычный DNS

1. **Сначала верните Станции её исходный профиль DNS** — обычно профиль по умолчанию сегмента, если он был исходным. Не меняйте профиль остальных клиентов. Оставьте тестовый резолвер работающим до переключения.
2. Обновите DHCP/соединение и DNS-кэш Станции; дождитесь TTL/очистите относящиеся к тесту кэши. Проверьте восстановление обычного DNS-пути.
3. Удалите **только созданные для этого теста** rewrites и отдельный профиль; профиль удаляйте после снятия назначения. Для встроенного DNS установите `[dns].enabled = false`, отправьте SIGHUP; HTTP/voice продолжат работу. Удаление Docker DNS port mappings требует recreate. Не удаляйте чужие правила или общий DNS-сервис.
4. Уберите **только добавленные нами LAN-публикации портов**/их override и точечные правила доступа. Верните базовые loopback-публикации Compose, если меняли способ запуска. Не очищайте всю таблицу firewall/NAT и не удаляйте чужие port mappings.
5. Отмените только собственные дополнительные изменения `public_uniproxy_url`, доверия сертификатам и IPv6, если делали их отдельно; секретные ключи не публикуйте. DHCP-резервацию удаляйте лишь если создали её для опыта и она больше не нужна.
6. Повторно проверьте Станцию и другой клиент: обычные DNS-ответы, HTTPS и приложения. При проблемах сравните с резервной копией; полное восстановление роутера — отдельное действие, не первый шаг отката.

## Почему не `ip host` и не DNS-based routes

В [официальном примере CNAME](https://support.keenetic.ru/ultra/kn-1811/ru/47184-configuring-dns-alias-cname.html) подтверждены формы `ip host DOMAIN cname TARGET`, `no ip host DOMAIN` и сохранение `system configuration save`. Это настройки DNS-прокси **роутера**, не правило для MAC; их нельзя считать изолированными для Станции. Здесь они не применяются. Синтаксис создания A-записи этой статьёй не подтверждён, поэтому команды для A-записи не приводятся. Команды вида «`ip host` для конкретного MAC» не предлагаются.

[DNS-based routes в KeeneticOS 5.0+](https://support.keenetic.ru/ultra/kn-1811/ru/51150-dns-based-routes.html) выбирают маршрут к исходным IP домена. Они **не заменяют DNS-ответ на `SERVER_IP`**, не меняют адрес назначения на локальный сервер и не превращают `quasard` в прокси.

Старые примеры OpenWRT/перехвата TLS в [TRAFFIC_CAPTURE.md](TRAFFIC_CAPTURE.md) относятся к другой ОС и исследовательскому стенду. Не выполняйте их на Keenetic и не переносите оттуда широкие правила в эту схему.
